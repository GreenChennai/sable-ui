> 本册是"宣称即证据"纪律的常驻文本(GATE-03,迭代审查报告 2026-10-04 §4.8)。
> 所有"已实现/全绿"的宣称必须能被本册列出的可复现命令证伪;所有门禁必须有
> 反面测试与显式扫描面。状态标记:**✅ 在岗**(CI 或本地门禁真实运行)/**▣ 本地

## 1. 三条纪律(照搬上游 v2 报告 §8.2,全员适用)

### 纪律① 宣称即证据

任何"已实现/已修复/全绿"的宣称,必须同时给出**可复现命令 + 退出码**(或 CI
job 链接)。不允许"我跑过、是好的"这类无锚点表述。文档中每处"✅ 已实现"
应尽量附模块路径;每处门禁宣称应附命令(本册 §3 即清单)。

- 反例(禁止):"tokens 同步检查已加好了"。
- 正例:"tokens 同步检查已加好:`cargo test -p sable-widgets --test gate_tokens_sync`,退出码 0(2026-10-04 本机)"。

### 纪律② 门禁要有反面测试

每条门禁必须自带"注入缺陷 → 红"的用例,证明门禁真的会红,而不是恒绿的
装饰品。反面用例与门禁同文件、同 CI 执行。

- 本轮样例:`gate_no_hardcoded_color.rs` 的
  `negative_numeric_arg_color_calls_are_flagged` / `negative_hex_literals_are_flagged`
  喂入 `rgba(1,2,3,1)`、`"#aabbcc"` 必须命中;`positive_clean_code_passes`
  证明干净代码不误伤;`negative_test_region_does_not_leak_after_close`
  证明 `#[cfg(test)]` 区域跟踪闭合后不失灵。

### 纪律③ 门禁扫描面显式化

每条门禁必须写明:**扫哪些路径、豁免哪些路径、判定规则是什么**。禁止"扫全仓"
这类模糊表述。豁免必须逐条带原因,且豁免指向的文件不存在时门禁要红(防
改名后死豁免)。各门禁的扫描面见 §3 表格"扫描面"列;硬编码色门禁的完整
规则见 `crates/sable-widgets/tests/gate_no_hardcoded_color.rs` 模块文档。

## 2. 门禁为什么长这样(红线背景)

- **ARL-1.0 / ACL-1.0**:上游 CutForge / VellumBench 代码**禁止抄写**,其 crate
  (`vb_*`、`cutforge-*`)不得出现在本仓依赖图——`cargo tree` 红线断言 + cargo-deny
  双保险。
- **零硬编码色**:`tokens.rs` 是全 workspace 唯一允许定义颜色字面量的文件
  (单一真相源);`theme.rs` 集中定义画布语义色。组件直接写色值 = 深浅主题
  立即出现"漏网之色",无法一键换肤。
- **CHANGELOG 纪律**:触及 `crates/**` 或 `examples/**` 的提交必须同步
  CHANGELOG(Unreleased 段),防止发布时凭记忆补写变更。

## 4. 维护约定

- 新增门禁:先在本册 §3 建行(扫描面/规则/反面测试三列不许留空),再落代码;
  计划态门禁进 §3.2,落地后迁 §3.1 并附复现命令。
- 新增豁免:必须带原因写入对应豁免文件;豁免文件格式自校验(条目指向的
  文件不存在 → 门禁红)。
- 门禁变红时的第一反应不是豁免,而是判断:**代码错** 还是 **门禁过时**;
  两者都不是才谈豁免,且豁免要过评审(本册 git blame 可追溯)。
