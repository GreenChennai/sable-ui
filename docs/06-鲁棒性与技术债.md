## 1. 鲁棒性:够不够强?——不够,补强方案如下

原方案(分册一~五)覆盖了"正常路径",鲁棒性要解决的是**异常路径**。设计软件的异常路径有六类,逐类给方案:

### 1.1 GPU 设备丢失(Device Lost)——✅ 已实现

驱动更新、显卡休眠、显存耗尽都会导致 GPU device 丢失。**不处理 = 用户工作全丢 + 进程崩溃**。

以下为 `crates/lumina-paint/src/gpu.rs` 的**已实现版本**(与原稿的差异全部源于 wgpu 30 的 API 变化,见 §6.3):

```rust
// lumina-paint/src/gpu.rs(已实现,节选)
pub struct GpuGuard {
    device: wgpu::Device,
    queue: wgpu::Queue,
    generation: Arc<AtomicU64>,        // device 代数,缓存全部按代数失效
}

/// 单帧渲染的可重试分类(替代已删除的 wgpu::SurfaceError):
/// 设备丢失类失败可重建后重试,其余一律致命。
pub enum FrameError {
    Retryable(String),   // CurrentSurfaceTexture::Lost / Outdated
    Fatal(String),       // 校验错误、超时、OOM 等
}

/// 把 wgpu 30 的 CurrentSurfaceTexture 分类成 FrameError
/// (Success/Suboptimal/Occluded = 可用;Lost/Outdated = 可重试;其余致命)。
pub fn classify_surface_result(status: &wgpu::CurrentSurfaceTexture) -> Option<FrameError> { /* … */ }

impl GpuGuard {
    /// 包装现有 device/queue;uncaptured error 只记录不 panic(wgpu 30:handler 是 Arc)。
    pub fn new(device: wgpu::Device, queue: wgpu::Queue) -> Self {
        // device.on_uncaptured_error(Arc::new(|error| tracing::error!(...)));
        Self { device, queue, generation: Arc::new(AtomicU64::new(0)) }
    }

    /// 当前设备代数;每次重建自增 1。代数句柄交给一切 GPU 资源缓存做
    /// (generation, resource) 失效配对 —— 代数对不上即重建。
    pub fn generation(&self) -> u64 { /* … */ }
    pub fn generation_handle(&self) -> Arc<AtomicU64> { /* … */ }

    /// 每帧渲染入口:可重试失败 → 重建 device、代数 +1、重试一次;二次失败才算致命。
    /// f 会被调用至多两次,须为幂等的帧构建闭包(Fn)。
    /// 与原稿差异:SurfaceError 已从 wgpu 30 移除,可重试性由 FrameError 表达;
    /// 恢复异步化以复用 request_device。
    pub async fn render_with_recovery<T>(
        &mut self,
        adapter: &wgpu::Adapter,
        f: impl Fn(&wgpu::Device, &wgpu::Queue) -> Result<T, FrameError>,
    ) -> PaintResult<T> { /* … */ }
}
// 配套纪律:一切 GPU 资源缓存(vello renderer、纹理、管线)都存 (generation, resource),
// generation 对不上自动重建 —— 这就是"device lost 后用户无感"的全部秘密。
```

### 1.2 崩溃不丢稿(自动保存 + 原子写)——✅ 已实现

Illustrator 和剪映都有崩溃恢复,这不是加分项是底线:

```rust

/// 原子写:先写临时文件,fsync,再 rename —— 写到一半断电也不会得到半个文件。

pub fn atomic_write(path: &Path, data: &[u8]) -> io::Result<()> { /* … */ }

/// 自动保存目录:%APPDATA%/{app}/autosave(Windows);Unix 用 $XDG_DATA_HOME。
/// 崩溃后下次启动检测 autosave 目录 → 弹"恢复未保存的工作?"
pub fn autosave_dir(app_name: &str) -> PathBuf { /* … */ }

/// 自动保存计划:目录 + 轮换保留份数(按 mtime 从新到旧保留 keep 份)。
/// 挂到 History::undo_len:每 30 个未存命令或 60 秒触发一次 write + rotate。
pub struct AutosavePlan { pub dir: PathBuf, pub keep: usize }
```

**配套铁律**:文档模型必须随时可完整序列化(§5.1 的 MessagePack 格式)。**v0.1 已验收**:`Scene` 全量 serde + slotmap serde 往返测试通过(`scene_serde_roundtrip_preserves_data_and_keys`)—— 这条在命令系统落地时就验证了,不是 M4 才发现某个字段没法序列化。

### 1.3 恶意/损坏文件输入

打开别人给的 .lumi/.svg/.mp4 是最大攻击面和崩溃面:

| 输入 | 风险 | 初期对策 | v0.1 |
|---|---|---|---|
| 工程文件 | 畸形 MessagePack → panic/OOM | `serde` 反序列化全程 `Result`;大小上限预检(声明大小 vs 实际);**fuzz 测试(`cargo-fuzz`)从 M2 接入 CI** | ☐(Scene serde Result 化 ✅,fuzz 未接) |
| SVG | 亿万级路径节点 → OOM | usvg 解析后节点数上限(默认 100 万,可配);超限时提示降级导入 | ☐ M2 |
| 视频 | ffmpeg 崩溃 | **解码放独立子进程**(M4 起),主进程通过 IPC 取帧 —— 剪映/PR 都这么做,解码器崩了主程序不崩。CutForge 同思路:内核/壳进程隔离 | ☐ M4(硬门槛) |
| 字体 | 畸形字体塑形崩溃 | 塑形包 `catch_unwind` + 字体黑名单 | ☐ M2(文本工具落地时) |

### 1.4 数值鲁棒性——✅ 纪律已落地

```rust
// 世界坐标一律 f64(kurbo 原生)——f32 在 1e6 坐标下精度只剩 0.06px,贝塞尔求交会炸
// 只在交给 GPU 的最后一刻(vello scene 构建)转 f32,且以可见区为中心做相对变换
pub fn scene_to_gpu(path: &BezPath, viewport_origin: Point) -> BezPath {
    Affine::translate((-viewport_origin.x, -viewport_origin.y)) * path  // 原点归位再降精度
}

```

v0.1 现状:`Viewport`/`Scene`/`Command` 全链 f64(kurbo 原生,AGENTS.md §3.6 固化为纪律);f32 降级目前只发生在 peniko 渐变几何(`style.rs` 的 radius as f32)与 vello_cpu 内部 —— peniko 0.6 的渐变坐标 API 事实如此,归位变换在 canvas 层接入时一并做。

### 1.5 并发与内存

- 解码/缩略图线程**全部有界队列**(容量 2~8),杜绝"后台产帧比前台消费快 → 内存涨爆"
- 全局内存预算器:解码缓存 512MB + 缩略图 256MB + 撤销栈上限(文档大小 20%),超限 LRU 驱逐
- `unsafe` 禁令:**workspace 级纪律已落地**(`lumina-paint` 用 `#![forbid(unsafe_code)]`,AGENTS.md §3.2 全 workspace deny;v0.1 不接 ffmpeg 原生绑定,连豁免层都不需要 —— 原计划的 `lumina-ffi` 在 M4 之前不存在)

### 1.6 鲁棒性验收(写进 CI)

- [ ] 渲染循环中拔掉 GPU(`dxcap` 强制 device lost / `WGPU_BACKEND=noop` 模拟)→ 自动恢复不崩溃(GpuGuard 已实现,此验收待 CI 化)
- [ ] 自动保存:kill -9 进程 → 重启恢复到最后 60 秒内状态(原子写/轮换已实现并有测试,进程级验收待宿主接入)
- [ ] 10 万个畸形 fuzz 样本喂工程文件解析器 → 零 panic

## 2. 耦合性:够不够低?+ 小软件能不能只用分库?

**能,这正是 workspace 分 crate 的意义。** 但要做到"只用分库不打包整个 UI 库",需要显式的 feature 设计和依赖纪律。以下是正式规约:

### 2.1 依赖金字塔(编译期强制单向;✅ 已按此落地,一处偏差)

```
        ┌─────────────┐
        │ lumina-video │  依赖:core(★ 2026-10 决策:不再依赖 canvas,理由见 §8)
        ├─────────────┤
        │lumina-widgets│  依赖:canvas + core + gpui(gpui 是组件层的身份,见 §2.3 注)
        ├─────────────┤
        │ lumina-canvas│  依赖:paint + core(gpui 为 optional feature)
        ├─────────────┤
        │ lumina-paint │  依赖:core(+ vello/wgpu 或 vello_cpu,feature 门控)
        ├─────────────┤
        │  lumina-core │  依赖:仅 kurbo/slotmap/serde/thiserror —— 零 UI 框架依赖
        └─────────────┘
```

> **白名单修正(2026-10)**:core 原白名单写的 `kurbo/peniko/serde/slotmap`,**peniko 已移除** —— 场景图用自有 `Paint` 枚举(serde 友好),peniko 转换下沉到 lumina-paint(`style.rs`)。见 [02-渲染与画布.md](02-渲染与画布.md) §3。

### 2.2 Feature 矩阵(✅ 已实现于 `crates/lumina/Cargo.toml`)

```toml
# lumina/Cargo.toml —— 门面 crate,用户按场景点菜(与仓库实际一致)
[features]
default = ["full"]
# —— 整套餐 ——
full    = ["canvas", "widgets", "dock", "video"]
# —— 单点场景 ——
core    = ["dep:lumina-core"]                        # 只要数据模型/命令系统
canvas  = ["core", "dep:lumina-canvas", "lumina-canvas/gpui"]
widgets = ["canvas", "dep:lumina-widgets"]
dock    = ["widgets", "dep:lumina-dock"]
video   = ["canvas", "dep:lumina-video"]
# —— 渲染后端三选一(见 §6)——
backend-vulkan = ["lumina-paint/backend-vulkan"]
backend-dx12   = ["lumina-paint/backend-dx12"]
backend-auto   = ["lumina-paint/backend-auto"]
# —— CPU 兜底(无 GPU 环境/服务器渲染)——
cpu-render = ["lumina-paint/cpu"]
```

### 2.3 典型"只用分库"场景

| 场景 | 依赖写法 | 打包进去的东西 |
|---|---|---|
| 服务器端 SVG→PNG 渲染 | `lumina = { features = ["core", "cpu-render"], default-features = false }` | 无 GPUI、无 GPU 依赖,纯 CPU |
| CLI 工具要命令系统/工程格式 | `lumina = { features = ["core"], default-features = false }` | 仅 kurbo/slotmap/serde,约 2MB |
| 小型工具要画布不要视频 | `lumina = { features = ["canvas"], default-features = false }` | 无 ffmpeg(省 ~40MB DLL) |
| 只要色轮/数值框两三个组件 | 直接依赖 `lumina-widgets` + 组件级 feature:`features = ["color", "number-field"]` | 组件级裁剪 |
| 完整设计软件 | `lumina = { features = ["full"] }` | 全家桶 |

```toml
# lumina-widgets/Cargo.toml —— 组件级 feature(小软件友好性的关键;✅ 已实现)
[features]
default = ["full"]
full = ["theme", "anim", "binding", "color", "number-field", "inspector", "layer-panel", "timeline", "curve-editor"]
theme = []
anim = []
binding = []
color = []          # ColorWheel/ColorWell/GradientEditor
number-field = []
inspector = ["number-field", "binding"]
layer-panel = []
timeline = []
curve-editor = []
node-graph = []
```

> **与原稿的一处修正**:widgets 的 `gpui` 在本仓库是**必选依赖**而非可选 —— "widgets 是 GPUI 形态的组件层,gpui 是它的身份而非可选依赖"(Cargo.toml 注释);真正"零 gpui"的场景请用 lumina-core / lumina-canvas(cpu-render)。依赖数据面(命令系统/场景模型)的复用不经过 widgets。

### 2.4 解耦的三条编译期护栏(CI 强制)

1. **依赖方向检查**:`cargo machete` + 自定义脚本校验依赖图无环、无跨层(widgets 不许直接依赖 video;video 不许反向依赖 canvas)
2. **框架隔离**:`lumina-core` 的 CI job 用 `--no-default-features` 单独编译,保证零 gpui 依赖永不回退
3. **公共 API 稳定面**:每个 crate 的 `pub` 项进 `cargo public-api` 快照 diff,breaking change 必须改 minor 版本

(三条护栏都依赖 §M0 的 CI,任务 0.4 未建前由 review 把关)

## 3. 审美:够不够现代?——建立设计 Token 系统

"现代"不是感觉,是一套**可执行的数值规范**。对标 Figma/Linear/剪映专业版 2026 年的设计语言,Lumina 的设计 token 体系(M0 落地,替代散落的魔法数字;**落点 `lumina-widgets::tokens`,feature `theme`;☐ 规划中**):

### 3.1 色阶系统(语义分层,不是散色)

```rust
// lumina-widgets/src/tokens.rs —— 所有组件只许用 token,不许写死颜色
pub struct ColorTokens {
    // —— 表面层(从深到浅 5 级,深色主题为例)——
    pub surface_0: Hsla,   // #0f0f12 应用底色
    pub surface_1: Hsla,   // #16161a 面板底
    pub surface_2: Hsla,   // #1e1e24 卡片/输入框
    pub surface_3: Hsla,   // #26262e hover 态
    pub surface_4: Hsla,   // #2f2f38 active/pressed
    // —— 边框 ——
    pub border_subtle: Hsla,  // white 6%
    pub border_strong: Hsla,  // white 12%(聚焦时)
    // —— 文本 ——
    pub text_primary: Hsla,    // white 92%
    pub text_secondary: Hsla,  // white 60%
    pub text_disabled: Hsla,   // white 32%
    // —— 强调色(品牌色,8 级色阶抄 Radix Colors 思路)——
    pub accent: Hsla,          // 选中/聚焦/主按钮
    pub accent_muted: Hsla,    // accent 20% 透明度(选中背景)
    // —— 功能色 ——
    pub danger: Hsla, pub warning: Hsla, pub success: Hsla,
    // —— 画布语义色(分册三 §5 的 CanvasTheme 并入此体系)——
    pub canvas: CanvasTheme,
}
```

> **命名空间纪律(上游教训,必须遵守)**:"软件外观色"与"用户内容色"分两个域(VB 的 `--vb-ui-*` vs `--vb-brand-*`;CutForge 的界面主题 vs 字幕/转场颜色)。tokens.rs 从第一天就分离,否则库层 token 会污染用户工程数据([upstream/02-vellumbench-ui-analysis.md](upstream/02-vellumbench-ui-analysis.md) §7.4)。
> **数值来源**:token 的具体色值/间距/圆角/动效四表直接取上游的客观数事实(如 vb-ui-tokens.json 的 17 色 × 2 主题、4 基数间距),这是"事实"不是"表达",ACL-1.0 允许对齐;机制上建 `lumina-tokens.json` 设计真相 + `tokens_sync` CI 测试(见 [upstream/02-vellumbench-ui-analysis.md](upstream/02-vellumbench-ui-analysis.md) §6 步骤 1)。

### 3.2 数值规范(2026 现代桌面软件标准)

| Token | 值 | 说明 |
|---|---|---|
| 圆角 | 4 / 6 / 8 / 12 px | 控件 6,卡片 8,对话框 12(与 VellumBench 圆角档完全一致,可直接沿用) |
| 间距 | 4px 网格(4/8/12/16/24/32) | 一切 padding/gap 取此序列;"禁止 5/7/10/15/20"(VB 门禁测试同款纪律) |
| 控件高度 | 22(紧凑)/ 26(默认)/ 32(宽松) | **★ 2026-10 修正见下** |
| 字号 | 11 / 12 / 13 / 16 / 20 | 面板正文 12,标题 13 |
| 字体 | UI:Inter + 思源黑体(中文回退);等宽:JetBrains Mono | 数值用等宽 tabular-nums(VB 字体链 Inter→MiSans→系统 CJK 五族,语义可参照) |
| 图标 | Lucide(gpui-component 内置同款),16px 网格 | 保持全家一致;代码禁裸字形/emoji |
| 阴影 | 面板浮起:`0 2px 8px rgba(0,0,0,.24)`;对话框:`0 8px 32px rgba(0,0,0,.4)` | 深色主题阴影要更深 |
| 对比度 | 正文 ≥ 4.5:1(WCAG AA) | token 设计时已校验(VB 有 WCAG AA 实测门禁可对齐机制) |

> ### ★ 2026-10 落地决策:控件高度三档是"下限",不是定值
>
> 原规范"控件高度 22/26/32"易被读成固定档。**修正(已写进 AGENTS.md §3.4)**:
>
> **实际控件高度 = max(档位值, 文本实际行高 + 2×垂直 padding)**
>
> 依据:VellumBench 实证 —— CJK 字形的排版 galley 高 ≈ 字号 × 1.4~1.5,固定 22px 行高会**压 CJK 文字**(VellumBench 曾写死 18pt 导致文字压叠后改为行高派生制;详见 [upstream/02-vellumbench-ui-analysis.md](upstream/02-vellumbench-ui-analysis.md) §3.4)。落地形式:tokens.rs 提供 `control_height(compact|default|roomy)` 派生函数,按当前字体实测排一行代表串("字Ag0")取 galley 高 + 2×垂直 padding,三档只作下限钳制。文字承载控件(NumberField/输入框/工具按钮)一律走派生函数,禁止写死小行高。

### 3.3 现代感的三条军规

1. **微交互全覆盖**:每个可点元素必有 hover(+4% 亮度)/ pressed(+8% 亮度)/ focus(accent 描边)三态,过渡 120ms —— 没有三态的 UI 一眼"上古"(gpui-kit 的组件三态约定已在 NOTICE.md 登记)
2. **克制拟态**:不用玻璃拟态/大模糊(GPU 费且已过时),用"表面分层 + 1px 半透边框"的现代扁平
3. **主题即数据**:全部 token 走全局态(分册三 §5),换肤 = 换一份 token 表,组件零改动

## 4. 动画:GPUI 没有内置动画框架,自建一套(M0 骨架,M3 补全)

这是原方案的真空地带,必须补。设计三层动画架构(☐ 规划;feature `anim` 已在 lumina-widgets 预留):

### 4.1 三层动画模型

```
L1 微交互层:hover/按压/面板展开 —— Tween,120~250ms,ease-out
L2 物理层:拖拽惯性、滚动回弹、面板吸附 —— Spring(弹簧物理)
L3 内容层:时间轴关键帧、曲线变速 —— 关键帧插值(分册四 §9,业务侧)
```

```rust
// lumina-widgets/src/anim.rs(规划)
use kurbo::Point;
use std::time::{Duration, Instant};

/// 缓动函数(CSS 同款曲线,用 kurbo 三次贝塞尔求值——现成轮子)
pub fn easing(name: Easing) -> impl Fn(f64) -> f64 {
    // Easing::OutCubic 等预设 = 两个控制点的 CubicBez,对 x 求 y
    move |t| kurbo_ease_y(name.control_points(), t)
}

/// 弹簧(critically-damped 起步,参数:刚度/阻尼/质量)
pub struct Spring { pub stiffness: f64, pub damping: f64, pub mass: f64 }
impl Spring {
    pub const SNAPPY: Self = Self { stiffness: 400., damping: 28., mass: 1. };  // 面板
    pub const BOUNCY: Self = Self { stiffness: 300., damping: 15., mass: 1. };  // 弹窗
}

/// 一个动画值:UI 组件持有它,每帧读 value()
pub struct Animated<T: Lerp> {
    current: T, from: T, to: T,
    started: Instant, duration: Duration,
    ease: Easing,
}
impl<T: Lerp> Animated<T> {
    pub fn set(&mut self, to: T, duration: Duration, ease: Easing) {
        self.from = self.value();           // 从当前值接续(打断也平滑)
        self.to = to; self.started = Instant::now();
        self.duration = duration; self.ease = ease;
    }
    pub fn value(&self) -> T {
        let t = (self.started.elapsed().as_secs_f64() / self.duration.as_secs_f64()).min(1.0);
        self.from.lerp(&self.to, easing(self.ease)(t))
    }
    pub fn is_running(&self) -> bool { self.started.elapsed() < self.duration }
}

/// 与 GPUI 集成:动画运行期间持续请求下一帧
pub fn pump<T: Lerp>(anim: &Animated<T>, cx: &mut Context<impl Sized>) {
    if anim.is_running() { cx.request_animation_frame(); }  // GPUI 0.2 有帧请求 API
}
```

## 6. Vulkan 后端:事实、方案与代码

### 6.1 必须先讲清的三个事实

1. **GPUI 在 Windows 上是 DirectX 11 原生渲染器,不是 wgpu**(Zed 只把 Linux 迁到了 wgpu,且维护者明确无计划替换 Windows 原生后端)。→ 原分册二"画布与 GPUI 共享 wgpu device"的写法**仅 Linux 成立**,Windows 上必须改方案,本节就是修正。
2. **wgpu 在 Windows 上默认(PRIMARY)会自动选 DX12,不是 Vulkan**;且实测中 wgpu 的 Vulkan 后端在 Windows 的 compute 负载下明显慢于 DX12 后端(有 6 倍案例),还有 resize 卡死的已知 issue。
3. **Vello 构建在 wgpu 之上**,需要 compute shader;wgpu 的 Vulkan 后端本身成熟(wgpu-hal 的主力后端,ash 绑定),Vello 在其上运行无碍。

**结论先行**:正确的工程姿势是——**渲染后端做成编译期/运行期可切换,默认 auto(Windows→DX12),提供 vulkan 开关满足强制需求**。既拿到"高性能",又不被 Vulkan 的 Windows 驱动坑拖累。下面是完整方案(**后端选择与设备创建 ✅ 已实现于 `lumina-paint/src/gpu.rs`**)。

### 6.3 实现代码(✅ 已实现;API 依据:docs.rs/wgpu/30.0.1,与原稿的差异见注释)

```rust
// lumina-paint/src/gpu.rs —— 后端选择(编译期 feature + 运行期覆盖)【已实现】
/// 运行期后端覆盖的环境变量(设置界面写入后映射为此变量,重启生效)
pub const BACKEND_ENV: &str = "LUMINA_GPU_BACKEND";

/// 后端选择:环境变量 > 编译期 feature > 平台默认。
/// 编译期:backend-vulkan > backend-dx12 > backend-auto/无(= PRIMARY)。
pub fn select_backends() -> wgpu::Backends {
    match std::env::var(BACKEND_ENV) {
        Ok(value) => match value.trim().to_ascii_lowercase().as_str() {
            "vulkan" => wgpu::Backends::VULKAN,
            "dx12"   => wgpu::Backends::DX12,
            _ => compile_time_backends(),
        },
        Err(_) => compile_time_backends(),
    }
}

/// 创建 wgpu 实例。debug 构建开校验/调试标记,release 关闭。
pub fn create_instance() -> wgpu::Instance {
    let mut descriptor = wgpu::InstanceDescriptor::new_without_display_handle();
    descriptor.backends = select_backends();
    descriptor.flags = if cfg!(debug_assertions) {
        wgpu::InstanceFlags::VALIDATION | wgpu::InstanceFlags::DEBUG_MARKERS
    } else {
        wgpu::InstanceFlags::empty()
    };
    wgpu::Instance::new(descriptor)   // wgpu 30:按值取 descriptor
}

// 设备请求:离屏渲染,无 surface;启动日志记录后端(排查用户机器问题第一眼)
pub async fn create_device(instance: &wgpu::Instance)
    -> PaintResult<(wgpu::Adapter, wgpu::Device, wgpu::Queue)>
{
    let adapter = instance
        .request_adapter(&wgpu::RequestAdapterOptions {
            power_preference: wgpu::PowerPreference::HighPerformance, // 双显卡机器选独显
            compatible_surface: None,
            force_fallback_adapter: false,
            apply_limit_buckets: false,   // wgpu 30 新字段
        })
        .await
        .map_err(|_| PaintError::NoAdapter)?;   // ★ wgpu 30:返回 Result,不再是 Option

    let info = adapter.get_info();
    tracing::info!(adapter = %info.name, backend = ?info.backend,
                   driver = %info.driver, "选中 GPU adapter");

    let (device, queue) = adapter
        .request_device(&wgpu::DeviceDescriptor::default())
        .await
        .map_err(|e| PaintError::DeviceRequest(e.to_string()))?;
    install_error_handler(&device);   // on_uncaptured_error(Arc) —— 只记录不 panic
    Ok((adapter, device, queue))
}
```

**wgpu 30 相对原稿 API 的四处变化**(实现时已逐一核对 docs.rs 与源码):

| 原稿写法(wgpu 26 时代) | wgpu 30 实际 |
|---|---|
| `Instance::new(&InstanceDescriptor { .., ..Default::default() })` | `InstanceDescriptor` **无 `Default`**;`Instance::new` 按**值**取 descriptor;基座用 `InstanceDescriptor::new_without_display_handle()` |
| `request_adapter(...).await?` 返回 `Option` | 返回 **`Result`**(错误含原因文本) |
| `match Err(wgpu::SurfaceError::Lost \| Outdated \| ...)` | **`SurfaceError` 已移除**;`Surface::get_current_texture` 返回 `CurrentSurfaceTexture` 枚举,恢复逻辑改用自有 `FrameError` + `classify_surface_result`(§1.1) |
| `device.on_uncaptured_error(Box::new(..))` | handler 参数为 **`Arc<dyn UncapturedErrorHandler>`** |

### 6.4 跨 API 纹理桥(DX11 GPUI ⇄ Vulkan vello,零拷贝路径)与 CPU 兜底

```rust
// lumina-paint/src/bridge_win32.rs(规划,M1)
// 原理:Vulkan 侧用 VK_KHR_external_memory_win32 创建可导出纹理 →
//       拿 NT handle → GPUI 的 DX11 渲染器 OpenSharedResource1 打开 →
//       作为普通纹理画进画布区域 quad。同步走 keyed mutex (IDXGIKeyedMutex)。
//
// wgpu 暴露口(wgpu-hal vulkan backend):
//   hal_texture.export_win32_handle()  → windows::Win32 HANDLE
// GPUI 侧:
//   平台层已有 raw DX11 device 访问口(gpui::platform::windows 内部),
//   通过 gpui 的自定义 Element::paint 注入 ID3D11ShaderResourceView
//
// 同步纪律(必须遵守,否则花屏):
//   Vulkan 写完 → signal fence → DX11 端 keyed mutex acquire → 采样 → release
//   每帧一 acquire/release;两帧 in-flight 纹理轮换防读写冲突
```

```rust
//   RenderContext::new(width: u16, height: u16)          ← 尺寸是 u16 不是 u32

//       (cpu.rs 测试 fill_with_opacity_halves_alpha_on_transparent_base 已断言此语义)
```

**务实的降级链**(鲁棒性要求,按序尝试;✅ 前 2 级的抽象已就位):

1. NT handle 零拷贝共享(成功 → 每帧 < 0.1ms 桥接开销)☐ M1
2. 共享失败(驱动怪异)→ vello 渲染后 `copy_texture_to_buffer` 读回 + GPUI 图片上传(1080p 约 2~4ms,可接受的兜底)☐ M1
3. 无 Vulkan 设备 → 切 backend-auto(DX12)重试 ✅(`LUMINA_GPU_BACKEND` 运行期覆盖已实现)
4. 全部失败 → vello_cpu 软件渲染 + 提示用户升级驱动 ✅(`CpuRenderer` 已实现)

### 6.5 什么时候真的该选 Vulkan(给用户的决策表)

| 你的情况 | 建议 |
|---|---|
| 只做 Windows 发行,追求省心高性能 | **auto(DX12)**。实测更快,驱动最稳,Zed 同理保留 DX |
| 计划跨 Linux 发行 | 同一份 wgpu 代码,Linux 上 PRIMARY 自动就是 Vulkan,零额外工作 |
| 要 Vulkan 特有扩展(外部内存/信号量对接自家 Vulkan 视频管线、ML 推理框架) | 强制 `backend-vulkan`,wgpu-hal 已提供外部 fence/semaphore API |
| 学习/研究 Vulkan | `backend-vulkan` + `LUMINA_GPU_BACKEND=vulkan` + RenderDoc 抓帧(wgpu 内置 renderdoc 支持) |
| 目标用户可能有 2015 年前的老核显 | auto + vello_cpu 兜底;Vulkan 1.1 以下直接放弃 GPU 路径 |

> **一句话**:Vulkan 在 Lumina 里是"可切换的一等选项"而不是"唯一后端"——这正是 wgpu 抽象的价值,你的代码 0 行改动横跨 Vulkan/DX12/Metal。
